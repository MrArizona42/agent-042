# OAuth2 / OpenID Connect — Auth Design for agent-042

Google OAuth2 + OpenID Connect (OIDC) is used for user authentication. The standard is
**Authorization Code Flow with PKCE**: Google handles login, we handle sessions.

---

## 1. Glossary

| Term | What it is |
|---|---|
| **OAuth2** | A delegation protocol. Lets a third party (Google) confirm who the user is without us ever touching their password. |
| **OIDC (OpenID Connect)** | A thin identity layer on top of OAuth2. Adds the ID Token so we can learn *who* the user is, not just that they granted access. |
| **PKCE** | A security extension for the auth flow. The client generates a random secret, sends a hash of it up front, then proves the secret on exchange. Prevents code interception attacks. |
| **Authorization code** | A short-lived, single-use opaque string that Google sends to our callback URL after the user logs in. Useless on its own — must be exchanged for real tokens. |
| **ID Token** | A signed JWT issued by Google. Contains the user's identity: `sub` (stable unique ID), `email`, `name`, `picture`. We validate its signature and use it to identify the user. |
| **Access Token** | An opaque string issued by Google. Grants access to Google APIs. We store it only to enable silent token refresh. |
| **Refresh Token** | A long-lived opaque string. Used to get a new access token when the current one expires, without asking the user to log in again. Google refresh tokens do not rotate by default. |
| **Session ID** | A random UUID generated by our Gateway after successful login. The only credential we send to the browser (as an `HttpOnly` cookie). Everything else stays server-side. |
| **`state` parameter** | A random string generated before redirecting to Google. Stored temporarily in Redis. Validated when Google returns the user. Prevents CSRF attacks on the login flow. |
| **`sub` claim** | The `subject` field inside the ID Token. Google's permanent, unique identifier for a user. Used as the link between Google identity and our `users` table. |
| **JWKS** | JSON Web Key Set. Google's public keys endpoint. We fetch these to verify the ID Token signature. |

## 2. How Login and Normal Use Work — Step by Step

### First visit (not logged in)

1. The user opens `https://agent.antonlab.ru:8443` in their browser.
2. Nginx forwards the request to the Streamlit UI.
3. Streamlit calls `GET /auth/me` on the Gateway. The Gateway finds no session cookie → returns `401`.
4. Streamlit redirects the browser to `/auth/login`.

### Login

5. The Gateway generates a random `state` string and a PKCE `code_verifier`. It stores
   `state → code_verifier` in Redis with a 10-minute TTL.
6. The Gateway builds a Google authorization URL containing: `client_id`, `redirect_uri`,
   `scope=openid email profile`, `state`, `code_challenge` (SHA256 of the code_verifier),
   `access_type=offline`, `prompt=consent`.
7. The browser is redirected to `accounts.google.com`. The user sees Google's login form.
8. The user authenticates with Google. Google redirects the browser back to
   `https://agent.antonlab.ru:8443/auth/callback?code=AUTH_CODE&state=...`.

### Callback (handled entirely by the Gateway)

9. The Gateway reads the `state` from the callback, looks it up in Redis, retrieves the
   `code_verifier`, and deletes the Redis key. If `state` is missing or expired → reject.
10. The Gateway POSTs to `https://oauth2.googleapis.com/token` with: `code`, `code_verifier`,
    `client_id`, `client_secret`, `redirect_uri`. Google responds with an `access_token`,
    `id_token`, and `refresh_token`.
11. The Gateway validates the `id_token` signature against Google's JWKS public keys and checks
    that `iss=accounts.google.com`, `aud=<client_id>`, and `exp` is in the future.
12. The Gateway extracts `sub`, `email`, `name`, `picture` from the ID token and upserts a row
    in the `users` table in PostgreSQL (insert on first login, update name/picture on subsequent).
13. The Gateway creates a new random UUID as the `session_id`, stores
    `session:{session_id} → {user_id, access_token, refresh_token, expires_at}` in Redis with a
    24-hour TTL.
14. The Gateway responds with `Set-Cookie: session_id=<uuid>; HttpOnly; Secure; SameSite=Lax`
    and redirects the browser to `/`.

### Normal use (logged in)

15. Every subsequent request from the browser carries the `session_id` cookie automatically.
16. Streamlit sends the cookie to the Gateway via `GatewayClient`.
17. `AuthMiddleware` in the Gateway reads the cookie, looks up the session in Redis, and
    injects `user_id` and `session_id` into the request context.
18. If the access token is within 2 minutes of expiry, the middleware silently exchanges the
    refresh token with Google and updates the Redis session before continuing.
19. The chat route handler reads `request.state.user_id`, loads the conversation history from
    PostgreSQL for that user's session, calls the LLM, and persists the new messages back.
20. All `/v1/*` routes that receive no valid session cookie return `401` immediately — they
    never reach the LLM or RAG services.

### Logout

21. The user clicks Logout in the Streamlit sidebar.
22. Streamlit calls `POST /auth/logout` on the Gateway.
23. The Gateway deletes `session:{session_id}` from Redis and clears the cookie.
    The user's Google account session is unaffected.

## 3. Database Schema

New database `agent042` on the existing `postgres` container (separate from the Airflow DB).

```sql
CREATE TABLE users (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    provider   TEXT NOT NULL,                         -- 'google'
    sub        TEXT NOT NULL,                         -- Google's stable user ID
    email      TEXT,
    name       TEXT,
    picture    TEXT,
    created_at TIMESTAMPTZ DEFAULT now(),
    UNIQUE (provider, sub)
);

CREATE TABLE chat_sessions (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    UUID REFERENCES users(id) ON DELETE CASCADE,
    title      TEXT,                                  -- first user message, truncated
    created_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE chat_messages (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_id UUID REFERENCES chat_sessions(id) ON DELETE CASCADE,
    role       TEXT NOT NULL,                         -- 'user' | 'assistant' | 'system'
    content    TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now()
);
```

This replaces the ephemeral `st.session_state.messages` list. Chat history now survives page
refreshes and browser restarts. The sidebar can list past sessions; switching loads messages from DB.

Redis session record (existing Redis, new key namespace):
```
session:{uuid}      → { user_id, access_token, refresh_token, expires_at }  TTL 24h
oauth_state:{rand}  → { code_verifier }                                      TTL 10min
```

## 4. Security

| Concern | Mitigation |
|---|---|
| We never handle passwords | Google owns credential verification entirely. |
| Token exposure in browser | Only the opaque `session_id` cookie is sent to the browser. All JWTs stay server-side in Redis. |
| XSS token theft | Session cookie is `HttpOnly` — JavaScript cannot read it. |
| CSRF on the login callback | `state` parameter validated against a Redis key. Mismatched or expired state → request rejected. |
| Session fixation | A new `session_id` UUID is generated on every login. |
| Fast revocation | Deleting the Redis key invalidates the session immediately, regardless of token expiry. |
| Forged ID tokens | Signature verified against Google's JWKS on every login. `iss`, `aud`, and `exp` are all checked. |
| Tokens in URLs | Authorization code is single-use with a 10-minute TTL. All other tokens are exchanged server-to-server over HTTPS, never in URLs. |
| Unauthorized API access | `AuthMiddleware` rejects all `/v1/*` requests with no valid session before they reach any service. |
| Old `.htpasswd` basic auth | Removed from Nginx. Application-level auth replaces it entirely. |

## 5. Implementation Plan

### Phase 0 — External setup (no code)

1. In [Google Cloud Console](https://console.cloud.google.com): create a project, create an
   **OAuth 2.0 Web Client**, set the redirect URI to
   `https://agent.antonlab.ru:8443/auth/callback`, add scopes `openid email profile`, and
   add all thesis user emails to the **Test users** list.
2. Add to `.env`:
   ```
   GATEWAY_GOOGLE_CLIENT_ID=...
   GATEWAY_GOOGLE_CLIENT_SECRET=...
   GATEWAY_GOOGLE_REDIRECT_URI=https://agent.antonlab.ru:8443/auth/callback
   GATEWAY_AGENT042_DB_URL=postgresql+asyncpg://postgres:<pw>@postgres:5432/agent042
   GATEWAY_SESSION_SECRET_KEY=<32-byte random hex>
   GATEWAY_SESSION_TTL_SECONDS=86400
   ```
3. Create the `agent042` database on the running `postgres` container:
   ```sql
   CREATE DATABASE agent042;
   ```

`docker-compose.yaml` requires **no changes** — Google is external, no new container needed.

### Phase 3 — Auth package (`src/gateway/auth/`)

Four files:

**`oidc.py`** — wraps `authlib` OIDC client.
- Fetches and caches Google JWKS.
- `build_authorization_url(state, code_challenge)` → redirect URL with `access_type=offline&prompt=consent`.
- `exchange_code(code, code_verifier)` → calls `oauth2.googleapis.com/token`, returns token triple.
- `validate_id_token(id_token)` → verifies RS256 signature, `iss`, `aud`, `exp`; returns claims dict.
- `refresh_access_token(refresh_token)` → returns new access + ID tokens.

**`session.py`** — wraps Redis session operations.
- `create_session(user_id, access_token, refresh_token, expires_in)` → write to Redis, return session UUID.
- `get_session(session_id)` → return dict or `None`.
- `delete_session(session_id)` → remove from Redis.
- `store_oauth_state(state, code_verifier)` → write `oauth_state:{state}` with 10-min TTL.
- `consume_oauth_state(state)` → atomic GET+DEL, return `code_verifier` or raise.

**`middleware.py`** — `AuthMiddleware(BaseHTTPMiddleware)`.
- Skip: `/health`, `/auth/*`, `/docs`, `/openapi.json`.
- All other requests: read `session_id` cookie (or `Authorization: Bearer` header).
- Redis miss → `401` JSON. Near-expiry access token → refresh transparently.
- Inject `request.state.user_id` and `request.state.session_id`.

**`router.py`** — FastAPI router at `/auth`.
- `GET /auth/login` → generate PKCE + state, store in Redis, redirect to Google.
- `GET /auth/callback` → validate state, exchange code, validate ID token, upsert user, create session, set cookie, redirect to `/`.
- `POST /auth/logout` → delete Redis session, clear cookie.
- `GET /auth/me` → return `{user_id, email, name, picture}` from session.

Register in `src/gateway/main.py`:
```python
from gateway.auth.middleware import AuthMiddleware
from gateway.auth.router import router as auth_router
app.add_middleware(AuthMiddleware)
app.include_router(auth_router)
```

Add to `pyproject.toml`: `authlib>=1.3`, `PyJWT[cryptography]>=2.8`.

### Phase 4 — Chat session API (`src/gateway/api/v1/chat_sessions.py`)

New routes, all protected by `AuthMiddleware`, all scoped to `request.state.user_id`:
```
POST   /v1/chat/sessions                        → create session, return id + title
GET    /v1/chat/sessions                        → list user's sessions (id, title, updated_at)
GET    /v1/chat/sessions/{session_id}/messages  → return message list for a session
DELETE /v1/chat/sessions/{session_id}           → delete session + cascade messages
```

Ownership enforced in DB queries (never trust the client to declare their own `user_id`).

### Phase 5 — Persist chat history (`src/gateway/services/processing.py`)

**`src/gateway/schemas/openai_chat.py`**: add `chat_session_id: str | None = Field(default=None)`.

`X-Chat-Session-ID` header before calling `process_chat`; auto-create a session if absent.

- Load existing messages from PostgreSQL for the given `chat_session_id` instead of the
  full client-supplied history.
- After generation, persist user + assistant messages and bump `chat_sessions.updated_at`.

### Phase 6 — Streamlit UI (`src/ui/app.py` + `src/ui/client.py`)

**`client.py`**: refactor to use a persistent `requests.Session` (cookie jar stays alive).
Add methods: `me()`, `create_chat_session()`, `list_chat_sessions()`, `get_session_messages(id)`.

**`app.py`**:
1. On load: call `me()`. On `401` → redirect to `/auth/login` via `st.query_params` + `st.stop()`.
2. Sidebar: show user name + picture + Logout button.
3. Sidebar: list past chat sessions; clicking one loads its messages from DB.
4. On new session or first load: call `create_chat_session()`, store UUID in `st.session_state`.
5. Send only the new user message + `chat_session_id` per request (not full history).
