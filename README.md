# Agent 042.

Проект "Agent 042" имеет в себе 2 основные цели:
1. Создание AI ассистента для исследователей в области ML/DL/AI/LLM, который работает полностью на локальном оборудовании, обеспечивая конфиденциальность данных.
2. Построение платформы production уровня для инференса и экспериментов.

В сумме, проект позволяет получить полезный продукт (ассистент) и при этом служит песочницей для отработки полного цикла MLOps задач: от экспериментов и версионирования до деплоя и мониторинга.

## Инференс-платформа

Платформа обслуживает запросы пользователей в режиме реального времени. Точка входа — nginx (TLS, Let's Encrypt), который маршрутизирует трафик по путям: `/` — Streamlit UI, `/api/` — FastAPI Gateway, `/auth/` — OAuth-эндпоинты.

**Путь запроса (асинхронный режим):**
браузер → nginx (WebSocket) → Streamlit → Gateway (HTTP + SSE) → RabbitMQ (Task ID) → Celery Worker → vLLM → Redis pub/sub → Gateway SSE → Streamlit (WebSocket) → nginx (WebSocket) → браузер.

- **Браузер** — отправляет сообщение через WebSocket-соединение, открытое Streamlit
- **nginx** — проксирует WebSocket-трафик к контейнеру Streamlit
- **Streamlit** — получает ввод пользователя, делает HTTP-запрос к Gateway, стримит ответ обратно в браузер по тому же WebSocket
- **FastAPI Gateway** — принимает запрос, запускает RAG-query (если включено), формирует промпт, публикует задачу в RabbitMQ и подписывается на Redis-канал для получения токенов
- **RabbitMQ** — принимает Task ID задачи в очередь и доставляет его первому свободному Celery Worker
- **Celery Worker** — забирает задачу из очереди, вызывает vLLM через OpenAI-совместимый API, получает токены и публикует каждый токен ответа в Redis pub/sub канал `tokens:{task_id}`
- **vLLM** — генерирует токены с применением нужного LoRA-адаптера (multi-LoRA), стримит их обратно в Worker
- **Redis** — транспорт токенов от Worker к Gateway через pub/sub канал; Gateway подписан на этот канал с момента отправки задачи
- **FastAPI Gateway** — получает токены из Redis и отдаёт их Streamlit в виде SSE-потока
- **Streamlit → браузер** — каждый новый токен отправляется в браузер по WebSocket

**FastAPI Gateway** выполняет несколько функций:
- **Auth layer** — OIDC/OAuth2 через Google, PKCE-flow, хранение сессий в Redis, защита от CSRF
- **User history management** — CRUD для `chat_sessions` и `chat_messages` в PostgreSQL
- **Task routing** — классификация запроса по ключевым словам (`chat` / `summarize` / `code`, планируется отдельный оркестратор)
- **Prompt builder** — формирование системного промпта под задачу (`chat` / `summarize` / `code`) с инъекцией RAG-контекста
- **Redirect logic** — OAuth-редиректы на Google и обратно
- **Discovery / introspection** — `/health`, `/config`, `/v1/models`, `/v1/knowledge-bases`

## Экспериментальная платформа

Платформа состоит из двух независимых треков, которые разделяют общую инфраструктуру хранения, но не имеют прямой связи между собой.

**LoRA-трек:**
Эксперименты по обучению LoRA-адаптеров под разные нужды (chat, summarize, code). Стэк:
* Запуск в JupyterLab или через Python скрипты
* Конфигурирование экспериментов через Hydra. Обертка в Pytorch Lightning для удобства логирования в MLflow и управления чекпоинтами
* Треккинг экспериментов в MLflow: метрики, параметры, артефакты (веса адаптеров)
* Registry для LoRA-адаптеров в MLflow Model Registry
* Remote storage: Yandex S3 для хранения весов адаптеров и артефактов экспериментов.
* Aliases для управления версиями адаптеров: `champion` (прод) и `challenger` (кандидат)

**RAG-трек:**
Эксперименты по сборке RAG системы. Стэк:
* JupyterLab и Python скрипты для скачивания датасетов, сборки индексов и оценки качества RAG
* Airflow для автоматизации сборки RAG-индексов по расписанию. DAG-и скачивают новые данные, обрабатывают их, генерируют эмбеддинги и загружают в Qdrant.
* Vector Store: Qdrant для хранения векторных представлений документов.
* Aliases. Каждая коллекция может иметь более одного alias, например: `champion` (для прод-запросов) и `challenger` (для новых сборок в экспериментах).

**Evaluation and benchmarking:**
* Запуск в Airflow, JupyterLab или через Python скрипты
* Оценка 3 видов задач: чат, суммаризация и кодинг. Для каждой задачи есть набор датасетов и метрик.
* Метрики для чата: ROUGE-L, BERTScore, relevance, correctness
* Метрикак для суммаризации: ROUGE-L, BERTScore, faithfulness, coverage
* Метрики для кодинга: pass@k, executable rate
* Метрикак для RAG: Recall@k, nDCG@k

## Хранилища

Проект использует пять типов хранилищ данных

**PostgreSQL (один инстанс, три базы данных):**
- `${POSTGRES_DB}` — бэкенд MLflow: эксперименты, запуски, метрики, параметры, теги, модели и их версии/алиасы
- `${AIRFLOW_DB}` — метаданные Airflow: DAG-runs, task instances, XComs, connections
- `agent042` — прикладная БД: пользователи (`users`), сессии (`chat_sessions`), сообщения (`chat_messages`), результаты бенчмарков (`eval_runs`)

**Qdrant:**
Векторные коллекции для RAG. Каждая база знаний (`arxiv`, `pytorch_docs`) имеет под одним или несколькими alias: `{kb}_champion` - прод-запросы, и `{kb}_challenger` - для экспериментов и тестоов. Метаданные коллекции хранятся внутри неё же в виде sentinel-точки с `id="_meta"`.

**Yandex Cloud S3 (два независимых префикса):**
- `mlflow/` — артефакты MLflow: веса LoRA-адаптеров, чекпоинты.
- `dvc/` — DVC remote: датасеты и RAG-корпуса (см. ниже)

**RabbitMQ:**
Транзитное хранилище задач. Каждая задача (Task ID + параметры запроса) попадает в очередь при поступлении от Gateway и удаляется сразу после того, как Celery Worker её забирает. Данные записываются на диск (`rabbitmq_data` volume) — это защищает от потери задач при перезапуске контейнера, но не предполагает долгосрочного хранения.

**Redis (один инстанс, два независимых соединения):**
- Pub/Sub канал `tokens:{conversation_id}` — стриминг токенов от Celery Worker к Gateway
- Key/value ключи `session:{uuid}` (TTL 24 ч) и `oauth_state:{state}` (TTL 10 мин) — хранение OAuth-сессий

## Версионирование

**Версионирование кода:**
- Git репозиторий, классический Git Flow.

**Датасеты (DVC → Yandex S3 `dvc/`):**

| Категория | Датасеты |
|---|---|
| Обучающие | `arxiv-summarization`, `open-code-instruct` |
| Оценочные | `hotpotqa`, `natural-questions`, `msmarco`, `beir-scifact`, `beir-nfcorpus` |
| RAG базы знаний | `arxiv`, `pytorch_docs` |

**LoRA-адаптеры (MLflow Model Registry):**
Каждый обученный адаптер регистрируется как отдельная модель в Registry. Веса хранятся в S3.

**Что не версионируется:**
- Базовая модель (монтируется из локального пути)

## Инфраструктура и эксплуатация

**Мониторинг:**
- **MLflow UI** — кривые обучения, таблицы параметров и метрик, сравнение экспериментов
- **Airflow UI** — статус DAG-запусков, логи задач, управление расписаниями
- **Flower** — мониторинг Celery-воркеров: очереди, статусы задач, throughput
- **RedisInsight** — инспекция ключей Redis: pub/sub каналы, сессионные ключи
- **RabbitMQ Management** — очереди, consumer-ы, метрики сообщений

**Развёртывание:**
- Текущее состояние: один сервер, Docker Compose. Все сервисы описаны в `infra/compose/docker-compose.yaml`.
- Планируется: k8s, Helm Charts, CI/CD.
